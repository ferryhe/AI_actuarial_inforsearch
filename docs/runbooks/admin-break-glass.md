# Admin break-glass recovery

Use this controlled, offline procedure only when every administrator is locked out.
It restores an active **email** administrator without weakening the application guard
that prevents removing the last one. Do not commit production passwords, database
copies, bootstrap tokens, or other credentials to this repository.

## Prerequisites

- Approved operator access to the host and the database storage.
- `sqlite3`, Docker tooling (when deployed with Docker), and a maintenance window.
- The email address or numeric ID of the approved recovery administrator. Use a
  password hash generated by the application's approved password-management process;
  never put a plaintext password in SQL, shell history, tickets, or source control.

For the Docker Compose deployment, the active named volume is normally
`ai_actuarial_inforsearch_ai-data`; its host path is
`/var/lib/docker/volumes/ai_actuarial_inforsearch_ai-data/_data`, and the database is
typically `index.db` in that directory. `/opt/ai_actuarial_inforsearch/data` may be a
stale host copy: confirm the running service's mount before using it.

## Offline database recovery

1. Identify and back up the active database before making changes. For example, after
   confirming the active volume and database file:

   ```bash
   sudo cp -a /var/lib/docker/volumes/ai_actuarial_inforsearch_ai-data/_data/index.db \
     /secure/backup/index.db.before-admin-recovery
   ```

2. Stop the application and ensure no other process can access the database. For a
   Compose deployment, run `docker compose stop app` (use the actual service name
   from `docker compose config --services`). Do not run SQLite writes against a live
   application database.

3. Prefer restoring an approved existing email user; substitute only reviewed
   placeholders and run this against the confirmed active DB:

   ```sql
   BEGIN IMMEDIATE;
   UPDATE users
   SET role = 'admin', is_active = 1
   WHERE id = <RECOVERY_USER_ID>;

   INSERT INTO audit_events (token_id, event_type, resource, detail, ip, created_at)
   VALUES (NULL, 'admin_break_glass_recovery', 'users/<RECOVERY_USER_ID>',
           '{"operator":"break-glass","result":"success"}', 'offline',
           CURRENT_TIMESTAMP);

   INSERT INTO user_activity_logs (user_id, ip_address, action, resource, detail, created_at)
   VALUES (<RECOVERY_USER_ID>, 'offline', 'admin_break_glass_recovery',
           'users/<RECOVERY_USER_ID>',
           '{"operator":"break-glass","result":"success"}', CURRENT_TIMESTAMP);
   COMMIT;
   ```

   If no approved user exists, first create one through the normal controlled bootstrap
   process or insert a record with a pre-generated approved password hash (never a
   plaintext password):

   ```sql
   INSERT INTO users (email, password_hash, role, is_active, email_verified, display_name, created_at)
   VALUES ('<RECOVERY_ADMIN_EMAIL>', '<APPROVED_PASSWORD_HASH>', 'admin', 1, 1,
           '<RECOVERY_ADMIN_DISPLAY_NAME>', CURRENT_TIMESTAMP);
   ```

   Record its resulting ID and insert the same `audit_events` and
   `user_activity_logs` records above. This ensures the manual recovery is visible in
   both audit surfaces.

4. Validate before restarting:

   ```sql
   SELECT COUNT(*) AS active_admins
   FROM users
   WHERE role = 'admin' AND is_active = 1;
   ```

   The result must be at least `1`. Inspect the changed user and the new audit row as
   a second check. Restart the service only after this validation.

## Controlled bootstrap alternative

When offline SQL is not permitted, a maintainer can set
`BOOTSTRAP_ADMIN_TOKEN=<BOOTSTRAP_ADMIN_TOKEN>` only in the protected runtime secret
store, start the service once, and use that admin credential to create or restore an
email administrator through the normal admin UI/API. The bootstrap mechanism creates
an admin token; it does not itself create an email user. Remove and rotate the
bootstrap token immediately after recovery, then confirm the active-email-admin count
above.

## Rollback and follow-up

- If recovery is incorrect, stop the service and restore the pre-change DB backup, or
  remove/demote the temporary recovery user only after another active email admin is
  confirmed.
- Rotate the temporary user's password and any bootstrap/admin tokens used in the
  event. Revoke temporary credentials according to the incident process.
- Preserve the incident record and verify `audit_events` and `user_activity_logs`
  contain the recovery action. Add an out-of-band incident/audit note if a direct SQL
  insert could not be recorded.
- Never commit production secrets, real hashes, tokens, database files, or backup
  paths containing sensitive data. All examples here are placeholders.
