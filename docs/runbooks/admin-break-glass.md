# Admin break-glass recovery

Use this controlled procedure only when every administrator is locked out. It
restores an approved active email administrator without weakening the
application guard that protects the last active admin. Do not commit production
passwords, database copies, bootstrap tokens, or other credentials.

Prefer the application flow: set `BOOTSTRAP_ADMIN_TOKEN` in the protected
runtime secret store, start the API, sign in with that token, and create or
restore the email administrator through the admin UI/API. The bootstrap token
creates an admin API token; it does not create an email user. Remove or rotate
the bootstrap token after recovery.

## Offline PostgreSQL recovery

Use direct SQL only when the application flow is unavailable and the database
operator has approved it. Set `DATABASE_URL` in the private process environment
and make a native PostgreSQL backup before the change. Do not copy or edit a
SQLite database file.

To promote an existing reviewed user, run the update and audit writes in one
transaction. Substitute only reviewed user IDs and approved audit details:

```sql
BEGIN;

UPDATE users
SET role = 'admin', is_active = TRUE
WHERE id = <RECOVERY_USER_ID>;

INSERT INTO audit_events (token_id, event_type, resource, detail, ip, created_at)
VALUES (NULL, 'admin_break_glass_recovery', 'users/<RECOVERY_USER_ID>',
        '{"operator":"break-glass","result":"success"}', 'offline', CURRENT_TIMESTAMP::text);

INSERT INTO user_activity_logs (user_id, ip_address, action, resource, detail, created_at)
VALUES (<RECOVERY_USER_ID>, 'offline', 'admin_break_glass_recovery',
        'users/<RECOVERY_USER_ID>',
        '{"operator":"break-glass","result":"success"}', CURRENT_TIMESTAMP::text);

COMMIT;
```

If no approved user exists, create one using a password hash generated by the
approved password-management process. Never place a plaintext password in SQL,
shell history, tickets, or source control:

```sql
INSERT INTO users (email, password_hash, role, is_active, email_verified,
                   display_name, created_at)
VALUES ('<RECOVERY_ADMIN_EMAIL>', '<APPROVED_PASSWORD_HASH>', 'admin', TRUE, TRUE,
        '<RECOVERY_ADMIN_DISPLAY_NAME>', CURRENT_TIMESTAMP::text)
RETURNING id;
```

Record the returned ID and insert the matching audit rows in the same
transaction. If any step fails, roll back before retrying.

Validate the active administrator count before restarting or closing the
incident:

```sql
SELECT COUNT(*) AS active_admins
FROM users
WHERE role = 'admin' AND is_active = TRUE;
```

The result must be at least `1`. Inspect the changed user and the audit rows as
a second check. Use only the intended PostgreSQL database named by
`DATABASE_URL`.

## Rollback and follow-up

- If recovery is incorrect, restore the verified PostgreSQL backup or correct
  the account only after another active email administrator is confirmed.
- Rotate temporary passwords, bootstrap tokens, and admin tokens used for the
  event.
- Preserve the incident record and verify `audit_events` and
  `user_activity_logs` contain the recovery entries.
